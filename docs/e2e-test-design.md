# E2Eテスト設計書

Playwright による本アプリのE2Eテストの設計・実装状況・カバレッジ分析。
実行方法や罠の要約は `CLAUDE.md` の「E2E Tests」も参照。

## 1. 目的と方針

- **目的**: リリース前に「ユーザーが実際に行う主要フロー」が壊れていないことを機械的に検証する。単体テスト(Vitest)がロジックを守るのに対し、E2Eは画面遷移・フォーム・確認ダイアログ・トーストといった統合された振る舞いを守る。
- **対象**: クリティカルパス(認証 → 食事記録 → 献立 → マスタ管理)と、過去に実バグがあった箇所のリグレッション防止を優先する。
- **非対象**: PWA(Service Worker・オフライン・プッシュ)は devサーバーで再現できないため対象外。OCRは画像フィクスチャが必要なため当面対象外。見た目(ダークモード等)はスクリーンショット比較を導入するまで対象外。

## 2. アーキテクチャ

| 項目 | 内容 |
|------|------|
| ランナー | Playwright(`playwright.config.ts`) |
| ブラウザ | Chromium / Pixel 7 エミュレーション(モバイルファーストのため) |
| 実行 | 先に `supabase start`。`pnpm test:e2e` がローカルの Supabase につないだ `next dev` をポート 3101 で自動起動(既存サーバーは再利用しない) |
| 並列性 | **直列実行**(`workers: 1`)。全テストが同一ユーザーのデータを変更するため |
| 認証 | `auth.setup.ts` がUIログインし `e2e/.auth/user.json`(gitignore)に storageState を保存。各テストはこれを再利用 |
| テストデータ | ローカルの Supabase だけを使う(`e2e/local-supabase.ts` がローカル以外なら止める)。`global.setup.ts` が毎回 `supabase db reset --local` してから E2E 用の利用者を3人作る: 共通の `e2e@example.com`(`e2eUser`)と、ログアウトを確かめる R-2 専用の `e2e-previous@example.com`・`e2e-next@example.com`(`e2eSwitchUsers`。ログアウトするとその利用者のセッションがすべて切れるため、共通の利用者を使わない) |
| リトライ | `retries: 1`(devサーバー起因のフレーク対策) |

### データライフサイクル

```
setup: サインイン(supabase-js) → 全データ削除 → UIログイン → storageState保存
テスト: 各テストが必要なデータを自分で作る(前のテストの残骸に依存しない ※例外あり、§5参照)
終了: クリーンアップなし(次回setupで消える)
```

### devサーバー特有の罠と対策(`e2e/helpers.ts`)

| 罠 | 症状 | 対策 |
|----|------|------|
| ハイドレーション前の入力 | DOMには値が見えるがreact-hook-formの内部状態に届かず、送信時に空扱い | `gotoHydrated`(networkidle待ち)+ `fillStable`(値が定着するまでリトライ)+ ログインは fill→submit→URL確認 を一体でリトライ |
| ハイドレーション前のクリック | ドロワー/モーダルを開くクリックが無反応 | `clickToReveal`(結果が見えるまでクリックをリトライ) |
| 開発ツールのオーバーレイ | TanStack Query devtools と Next.js devインジケータ(共に左下)がボトムナビ「ホーム」を遮る | `NEXT_PUBLIC_E2E=1` で両方無効化(`providers.tsx` / `next.config.ts`) |
| 認証レート制限 | 失敗ログインの繰り返しでエラー文言が変わる | 「正しくありません/試行回数が多すぎます」の両方を許容 |
| 隠れて残る画面 | `cacheComponents` で移動前の画面が `display: none` のまま DOM に残り、同じ文言・ラベルが2つ当たる(`getByRole` は数えないが `getByText`・`getByLabel` は数える) | `visibleText`・`visibleField` で見えている要素に絞る |
| 曜日依存 | 月曜は「昨日」が前週になり「実績を反映」の対象週が変わる | テスト内で曜日判定して前週へ移動 |

### 対象外(理由付き)

- **PWA/Service Worker**(更新プロンプト、オフライン、通知): devサーバーでSWが本番同等に動作しないため。本番スモークとして手動確認

- **ダークモードの見た目**: スクリーンショット回帰を導入する場合に検討

## 5. 既知の制約・注意

- **テスト間のデータ依存が一部ある**: 直列実行(spec名のアルファベット順)が前提。既知の依存:
  - M-1が朝食を埋めるため、M-2の `first()` は昼食を指す
  - meal-itemスペックは間食スロットのみを使い、meal-registrationの前提(朝食が空)を壊さない
  - **P-4はMI-2が残した「今日の間食の未転記プランE2Eポテチ」に依存**する(MI-2を変更する場合はP-4も見直すこと)
  - **QA-1はP-2が残した「昨日の夕食E2E実績ラーメン」と「今日の夕食が空」に、QA-2はM-2の「E2Eそば」に依存**する
  - SL-1は**翌週**のカレンダーを使う(今週のセルは他specの状態に依存するため。翌週は毎回wipe後に必ず空)
  - ドロワーを開く操作は `openSlotDrawer(page, スロット名)` を使う(スロット単位で特定するためリトライ時も冪等)
  - R-1 は `e2eUser` の今日の間食を使い、後で自分のアイテムだけを消す(間食は MI と P-4 も使う)
  - H-1〜H-3 と H-8 は、`e2eUser` の前日(H-8 は月曜なら翌日)の昼食を DB に直接入れ、後で `deleteMeals` で消す。H-4〜H-7 は今日と重ならない 2020-01-08〜10 を使う
  - P-2 の「前の日」はフェーズ 2 からリンク(`getByRole("link")`)
  - P-5〜P-7 は翌週の水曜の夕食(SL-1 が翌週の最初のセルを使うため)、P-9〜P-11 は他と重ならない 2020-02-03〜17 の週を使い、後で自分の献立だけ消す
  - P-12 は今日の夕食に献立を入れて転記し、後で今日の夕食の記録を消す(QA-1 が「今日の夕食が空」に依存するため)
  - 前後の週はフェーズ 3 からリンク(`getByRole("link")`)。P-2(月曜だけ)と SL-1 もリンクで取る
  - RC・FM はレシピ・マスタを DB に直接入れ、名前の前方一致で後から消す。FM-1 は今日の昼食に食事を1件足し、自分で作った行だけを消す(昼食の行が無ければ作り、作った行なら消す)
  - **dev サーバーは `'use cache: private'` の結果をリクエストをまたいで持つ**(cookie とヘッダーで区別。本番はサーバーに持たない)。全テストが同じ storageState なので、DB に直接入れたデータが、前のテストが開いた一覧のキャッシュに隠れる。RC・FM は `x-e2e-test-id` ヘッダーをテストごとに付けて、キャッシュをテストごとに分けている。引数の無い読み取り(一覧)を DB の直接書き込みで確かめるケースは同じようにする
  - ケース追加時は専用スロット・専用データ名(`E2E`プレフィックス)を使うこと
- **ローカルの Supabase を使用**(2026-10 まで本番の DB の専用アカウントで流していた)。DB はマイグレーションだけから毎回作り直すので、前回の実行のデータは残らない
- 設定系テストは引き続き初期値を仮定しない書き方を維持する(ST-1/ST-2)

## 6. 運用ルール

1. **新機能には対応するE2Eケースを追加する**(このドキュメントの§3と§4を更新)
2. **バグ修正時は、そのバグを再現するケースを追加してから直す**(リグレッション防止)
3. デプロイ前チェックは `pnpm lint` → `pnpm test:run` → `pnpm test:e2e` → `pnpm build`
4. セレクタは `getByRole` / `getByLabel` を優先(アクセシブルな実装を強制する副作用がある)。CSSクラスセレクタは禁止
